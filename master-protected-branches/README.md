# master-protected-branches

Runs `tarball-docker`, the entry point of every server build, and a few fast server builders that report their result to GitHub pull requests.

The name is historical. Builders on other masters report to GitHub too, and a builder doesn't have to be on this master to report.

## GitHub statuses and branch protection

Every master runs a `GitHubStatusPush` service ([master_common.py](../master_common.py)), which reports the builders listed in `GITHUB_STATUS_BUILDERS` in [constants.py](../constants.py) as `buildbot/<builder>`. Adding a builder to the list, whichever master runs it, makes it report its status. Which statuses are required before a pull request can merge is set in the branch protection rules of the GitHub repository.

A builder in `GITHUB_STATUS_BUILDERS`:

- is started by the `s_protected_branches` scheduler instead of `s_upstream_all`, and still has to be in `SUPPORTED_PLATFORMS` for the version;
- isn't limited by the worker locks;
- isn't generated by the autogen masters, even if its platform is in `os_info.yaml`, so it must be defined on another master (here, for `amd64-debian-12`, `aarch64-debian-11` and `amd64-fedora-43`).

A required status has to arrive soon, so these builders must be fast. The release builders on master-migration are too slow for this; see [Release builders](../master-migration/README.md#release-builders).

### Required checks

Reporting a status and requiring it are separate steps. Buildbot reports the status; making it a required check, so that a pull request can't merge until the builder passes, is done by an admin of the GitHub repository, in its branch protection rules (or rulesets), under the required status checks of the protected branches.

To add a required check:

1. Add the builder to `GITHUB_STATUS_BUILDERS`, and to `SUPPORTED_PLATFORMS` for every version whose branches the rule protects. A required builder missing from a version's list never reports on that version's pull requests, and blocks them.
1. Deploy it, and let it report on pull requests for a while, to see that it is reliable and fast. GitHub offers a check in its list only once the check has reported recently.
1. Ask a repository admin to require `buildbot/<builder>`.

To remove or rename a required check, have the admin remove it from the rules when the change is deployed, not after. Until then, every open pull request waits for a status that never comes, shown as "Expected — Waiting for status to be reported", and can't merge. Renaming a builder is removing one check and adding another.

## tarball-docker

On each change to MariaDB/server (see [master-web](../master-web/README.md)), `tarball-docker`:

1. stops, if it is building a push to a branch whose packages aren't saved, such as `bb-*`, and a pull request build of the same commit exists (`CancelDuplicateBuildRequests`). Pushes to the main and release branches always build;
1. cancels the older requests and running builds for the same branch, on every builder (`CancelOlderSameBranchRequests`);
1. clones the server and runs `make dist`;
1. sets `mariadb_version` from the source and `master_branch` from it (`11.8` for `mariadb-11.8.3`);
1. saves the source tarball under `<ARTIFACTS_URL>/<build number>/`. This build number is the `tarbuildnum` of every build that follows;
1. triggers `s_protected_branches` and `s_upstream_all`, or `s_jepsen` for `jpsn-*` branches.

Both cancel steps print what they cancelled and why, with links to the build requests.

Which builders run is decided by `SUPPORTED_PLATFORMS[master_branch]`. See [Server builders](../docs/server-builders.md) for the rest of the chain, and for adding a version or a platform.

## Workers

Docker latent workers on the `hz-bbw*` and `aarch64-bbw*` hosts. `tarball-docker` has two workers of its own, which save to `MASTER_PACKAGES_DIR`.
